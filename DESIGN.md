# Design: nextEnglish — Shadowing-First Pronunciation App

Generated by /office-hours on 2026-04-30
Owner: louis.nguyen@overdose.digital
Status: APPROVED
Mode: Builder

## Problem Statement

A 28yo IT engineer who works with global clients and runs an IT/AI YouTube channel
wants to sound native-like in technical and business English: clean pronunciation,
natural connected speech, confident phrasing. Existing apps (ELSA, Speechling,
BoldVoice) target generic learners with curated content. None of them let you say
"I want to sound like *this specific YouTuber*" and turn it into a daily practice
loop.

The owner has a rich pedagogical blueprint covering lexical chunks, the five
connected-speech mechanisms, discourse markers, IT/business idioms, PVSS
scripting, FSRS/SM-2, and second-brain capture. The blueprint is the long-term
vision. The wedge is shadowing.

## What Makes This Cool

1. **Paste-any-URL shadowing.** Drop a YouTube or podcast link, the app
   transcribes it, segments it, and turns it into shadowable practice. No more
   begging Speechling to add the speaker you actually want to imitate.
2. **Research-grade analysis on a desktop app.** WhisperX forced alignment plus
   Praat (via parselmouth) gives sub-100ms word timing and real pitch contours,
   not the toy DSP most learning apps ship.
3. **The same code is YouTube content.** Audio analysis prototyped in Jupyter
   notebooks drops directly into the Python sidecar, and the notebooks become
   videos for an IT/AI audience that loves this kind of teardown.
4. **Single-user, local-first, owns its data.** SQLite on disk, audio cached
   locally, no cloud round-trips during a session. Privacy and offline use are
   free side effects.

## Constraints

- **Timeline:** v1 ships in 3 weekends of focused work.
- **Audio analysis:** 100% local, no cloud during a session.
- **Cross-platform:** Windows-first (the owner's machine), Mac and Linux follow.
- **Owner skills:** Rust (shipped before), Python (assumed strong from AI
  channel), TypeScript (assumed competent). New Rust knowledge is fine; new
  ecosystem learning blows the timeline.
- **Scope:** Owner is also the only user for v1. No multi-user, auth, or sync.
- **Distribution for v1:** Local install on owner's own machine. Public release
  is v2+.

## Premises (agreed)

1. The wedge IS shadowing. SRS, conversation coach, capture-to-Obsidian, IT
   idioms, PVSS — all v2 or later.
2. The five connected-speech mechanisms (catenation, intrusion, elision,
   assimilation, palatalization) emerge from accurate shadowing; explicit drills
   are not in v1.
3. Audio analysis is fully local. Cloud is reserved for non-realtime LLM/coach
   features later.
4. Default feedback is one number going up plus word-level mispronunciation
   flags. Pitch contour and spectral views are a power-user toggle.
5. Curriculum (IT idioms, PVSS templates, business collocations) is data added
   over time, not a v1 feature.
6. Ship-by constraint: usable in 3 weekends. Anything heavier is v2.

## Approaches Considered

### Approach A: Electron + TS + bundled Python helper
Electron shell, React/TS UI, Python sidecar handles audio. Fastest predictable
distribution but heavier bundle and two-language debug paths.
- Effort: M (~3 weekends) — Risk: Low

### Approach B: Tauri + Rust + Python sidecar (RECOMMENDED, CHOSEN)
Tauri shell with a real Rust core, Python sidecar for audio analysis. Best
long-term architecture. Realistic in 3 weekends because owner has shipped Rust.
- Effort: M (~3 weekends with prior Rust) — Risk: Med

### Approach C: Pure Python + PyWebView
One language end-to-end, leverages the full Python audio stack, fastest to
notebook-to-app. Distribution friction (PyInstaller bundles ~2GB, Mac signing).
- Effort: S–M (~2 weekends) — Risk: Med (distribution)

## Recommended Approach: B — Tauri + Rust + Python sidecar

### Data Model

```sql
CREATE TABLE clip (
  id              INTEGER PRIMARY KEY,
  title           TEXT NOT NULL,
  source_uri      TEXT NOT NULL,        -- https://youtube.com/... or file://...
  audio_path      TEXT NOT NULL,        -- local 16k mono wav, vocals-only if isolated
  duration_ms     INTEGER NOT NULL,
  transcript_json TEXT NOT NULL,        -- whisperx output: [{word, start, end, score}]
  created_at      TEXT NOT NULL
);

CREATE TABLE segment (
  id        INTEGER PRIMARY KEY,
  clip_id   INTEGER NOT NULL REFERENCES clip(id) ON DELETE CASCADE,
  start_ms  INTEGER NOT NULL,
  end_ms    INTEGER NOT NULL,
  text      TEXT NOT NULL
);

CREATE TABLE session (
  id         INTEGER PRIMARY KEY,
  segment_id INTEGER NOT NULL REFERENCES segment(id) ON DELETE CASCADE,
  started_at TEXT NOT NULL,
  ended_at   TEXT
);

CREATE TABLE attempt (
  id                  INTEGER PRIMARY KEY,
  session_id          INTEGER NOT NULL REFERENCES session(id) ON DELETE CASCADE,
  attempt_audio_path  TEXT NOT NULL,
  asr_transcript      TEXT NOT NULL,
  score_overall       INTEGER NOT NULL,    -- 0-100
  score_word_accuracy REAL NOT NULL,       -- 0.0-1.0
  score_cadence       REAL NOT NULL,       -- 0.0-1.0 (1 - normalized DTW)
  score_pitch_corr    REAL,                -- nullable, Pearson on voiced frames
  recorded_at         TEXT NOT NULL
);

CREATE INDEX idx_segment_clip ON segment(clip_id);
CREATE INDEX idx_session_segment ON session(segment_id);
CREATE INDEX idx_attempt_session ON attempt(session_id);
```

### The Shadowing Loop (algorithm)

1. **Ingest** (UI: ClipPicker → Rust → Python `/ingest`)
   - URL: `yt-dlp -x --audio-format wav` → ffmpeg normalize to 16kHz mono.
   - File drop: ffmpeg normalize directly.
   - If music detected (energy in non-vocal bands above threshold), run
     `demucs --two-stems=vocals`. Demucs lazy-loaded; first run downloads model.
   - `faster-whisper` `medium.en` for transcript with sentence boundaries.
   - `whisperx` aligns words to audio using `wav2vec2-base` for sub-100ms
     timestamps.
   - Auto-segment into 5-15s chunks at sentence boundaries; persist clip +
     segments to SQLite.

2. **Pick segment** — UI lists segments with their text. User clicks one.
   Frontend plays the cached audio.

3. **Record attempt**
   - User taps Record. `MediaRecorder` captures 16kHz mono WebM/Opus.
   - On Stop, blob → Rust (`save_attempt`) → write to disk → invoke Python
     `/score` with paths to reference and attempt audio + reference transcript.

4. **Score** (Python `/score`)
   - ASR the user audio with `faster-whisper` → user transcript.
   - **Word accuracy**: word-level Levenshtein vs reference (case- and
     punctuation-insensitive). Output: 0.0–1.0 + per-word match flags.
   - **Cadence**: extract RMS energy at 10ms hops for both clips, run DTW
     (`librosa.sequence.dtw`), normalize the alignment cost by reference length.
     Score = `1 - normalized_cost`, clipped to [0, 1].
   - **Pitch correlation** (optional, computed always, shown only on toggle):
     `parselmouth` f0 contours, mask unvoiced frames, resample to common length,
     Pearson correlation.
   - **Overall**: `0.5 * word_accuracy + 0.4 * cadence + 0.1 * pitch_corr`,
     scaled to 0–100. Pitch correlation defaults to 0 contribution if unvoiced
     frames dominate (e.g., whispered).
   - Return JSON to Rust → frontend.

5. **Display** (ScoreCard)
   - Big number: overall 0–100.
   - Reference text rendered with mispronounced words highlighted red,
     missed words struck through.
   - "Try again" replays the original and re-arms recording.
   - "Show details" reveals PitchOverlay: f0 contour overlay, energy contour,
     DTW alignment heatmap.

6. **Persist** — Every attempt saves to SQLite with audio path. No cloud, no
   sync. v2 adds "favorite" → SRS pipeline.

### Rust ↔ Python protocol (v1)

JSON over HTTP on `127.0.0.1:<port>`. Port chosen by Python at startup, written
to stdout, captured by Rust. This avoids hardcoding ports and survives multiple
running instances.

```
GET  /health                                 → {ok: true}
POST /ingest      {source_uri, kind}         → {clip_id, segments: [...]}
POST /score       {ref_audio, ref_text,
                   user_audio}               → {overall, word_accuracy,
                                                cadence, pitch_corr,
                                                word_flags: [...]}
GET  /pitch       ?segment_id=… &attempt_id=…→ {ref_f0:[...], user_f0:[...]}
```

## Open Questions

1. **Whisper model default size.** `medium.en` (~1.5GB, best quality) vs
   `small.en` (~500MB, ~3x faster on CPU). Default to `medium.en` with a
   settings toggle. Revisit after first week of real use.
2. **Demucs cost.** Vocal isolation is great for music-backed clips but adds
   ~3GB and 30-60s per clip. Make it opt-in with auto-detection that *suggests*
   it. Don't run by default.
3. **Mic permissions on Windows.** Tauri's permission model is fine but the
   first-run UX needs a clear prompt. Test on a clean Windows VM before
   declaring v1 done.
4. **Cache eviction.** Audio + model files will balloon. Defer cache UI to v2;
   document the cache directory in the README.

## Eng Review Decisions (2026-04-30)

This section records decisions from `/plan-eng-review`. The original design above
is preserved as-is; the deltas below are authoritative when they conflict.

### Architecture decisions

**A1 — Mic audio format pipeline (decision: A1A).** Frontend uses MediaRecorder at
the browser's native sample rate (typically 48kHz on Windows) and ships
WebM/Opus to Rust. Python sidecar resamples to 16kHz mono via librosa
(`librosa.load(path, sr=16000, mono=True)`) before feeding faster-whisper.
*Why:* avoids hand-rolling AudioWorklet; keeps frontend code minimal.

**A2 — Sidecar lifecycle (just-fix).** Use Tauri's built-in `externalBin`
configuration in `tauri.conf.json`, not `Command::spawn`. This handles Windows
JobObject and Unix process-group cleanup automatically; no zombie Python
processes when the app crashes.

**A3 — First-run model download (decision: A3A).** Default model = `small.en`
(~500MB) for fastest first-run. After install, on first ingest, app shows an
opt-in card: "Better quality available — download medium.en (1.5GB)." Total
first-run download = `small.en` (500MB) + `wav2vec2` alignment (360MB) ≈ 860MB.
The download must:
- Have a clear progress UI in-app
- Resume on failure (HuggingFace `hf_hub_download` does this natively)
- Fail loudly on no-internet, with a "retry" affordance
- Be cancellable; partial files are cleaned up on cancel

**A4 — Error envelope (just-fix).** All Rust ↔ Python responses use a uniform
envelope: `{ok: true, data: {...}}` on success, `{ok: false, error: {code,
message, retryable}}` on failure. Defined error codes: `INVALID_URL`,
`DOWNLOAD_FAILED`, `CLIP_TOO_LONG`, `NO_SPEECH_DETECTED`, `TRANSCRIPTION_FAILED`,
`SCORE_FAILED`, `INTERNAL`. Rust matches on `code` to decide retry vs surface.

**A5 — Long-clip handling (decision: A5A).** Hard cap at 15 minutes. ClipPicker
validates duration client-side before sending. If over, the UI shows a built-in
trim widget (start/end sliders) so the user can pick a 15-min window and
re-submit. Long-form ingest is v2.

**A6 — Schema migrations (just-fix).** Add `schema_version` table from day 1:
```sql
CREATE TABLE schema_version (
  version INTEGER PRIMARY KEY,
  applied_at TEXT NOT NULL
);
INSERT INTO schema_version VALUES (1, datetime('now'));
```
On app startup, Rust reads the version and applies any pending migrations from
`src-tauri/migrations/`. v1 has no migrations; the table exists so v2 doesn't
need a retrofit.

**A7 — DTW silence trim (just-fix).** Before computing DTW between user and
reference RMS contours, run `silero-vad` on both clips to trim leading and
trailing silence. Otherwise a 200ms-late record-button click trashes the
cadence score. silero-vad is ~2MB and ~5ms/frame on CPU.

**A8 — Pitch correlation normalization (just-fix).** Z-normalize each f0
contour (subtract mean, divide by std) on voiced-only frames before computing
Pearson correlation. Without z-normalization, comparing the user's pitch range
to a different speaker's pitch range gives correlation values that are
mathematically valid but pedagogically meaningless.

### Code quality decisions (all just-fix)

- **C1** — Rust `models.rs` and Python `pipeline/models.py` both get
  cross-reference doc comments at the top pointing to each other. One
  integration test asserts a real Python response deserializes into the Rust
  type without panicking; if types drift, the test breaks.
- **C2** — Rust uses `tracing` + `tracing-subscriber` writing JSON-line logs
  to `app_data_dir/logs/nextenglish.rs.log`. Python uses `loguru` writing to
  `app_data_dir/logs/nextenglish.py.log`. When debugging "why is my score so
  low," `tail -f` both files.
- **C3** — Pin Python 3.11 in `pyproject.toml`. Both `parselmouth` and
  `whisperx` are stable on 3.11; 3.12+ has occasional torch wheel gaps.
- **C4** — Pin `pydantic >=2.6,<3` in `pyproject.toml`.
- **C5** — Frontend state: `zustand` (~1KB) for cross-component state (current
  clip, current segment, current attempt). Server state (clips, segments
  list) goes through `@tanstack/react-query` over Tauri commands.

### Test decisions (decision: T1A — focused subset)

Lands in v1:

- `sidecar/tests/test_ingest.py` — single test: 16-min synthetic audio →

Deferred to v1.1+:
- `test_analyze.py` (pitch/RMS edge cases) — added when calibration matters
- `db.rs` CRUD tests — thin glue, manual smoke is acceptable
- Playwright E2E — added when the UI stabilizes
- Real yt-dlp tests in CI — manual smoke only; CI fixtures are synthetic clips

### Performance decisions

**P1 — Cold start (decision: P1A).** Sidecar starts with stdlib + fastapi only.
torch / whisper / whisperx / parselmouth are imported **inside the handler**
on first use (one-time ~6s overhead). The frontend shows "preparing audio
engine…" during that first-of-session import. App launch itself is <3s warm.

**P4 — Demucs (just-fix).** demucs is **never** imported at sidecar startup. It
gets lazy-imported only when a user opts in to vocal isolation for a specific
clip. This keeps idle memory at ~3GB rather than ~7GB.

**P6 — wav2vec2 download (just-fix).** Folded into A3A's first-run flow. Total
first-run is 860MB across two models with sequential progress UI.

### Score-reveal psychology (decision 3A — editorial / instrument-panel)

The score is shown calmly, factually, like an instrument panel. No gauges, no
gamification, no encouraging copy. The user is treated as an adult who can
self-evaluate from numbers. Mispronounced words get a hairline underline, never
red. This decision is load-bearing for daily-return — see "Design decisions
deferred" below for the trajectory/sparkline question.

### Recording UX (just-fix)

5 beats: idle → listening (button grows, gradient-peach orb blooms, level meter
appears) → recording (level meter active) → stop → analyzing → score reveal.
Auto-play reference on Listening. Spacebar toggles record. Esc stops.

### NOT in scope (design)

Considered and explicitly deferred:

- **Light/dark mode toggle.** UI_DESIGN.md only specs light. Adding a dark
  variant means re-thinking gradient orbs (they'd need different stops on dark
  canvas). v2 work; many users practice at night so this matters eventually.
- **Animation timing detail beyond the table in UI_DESIGN.md extensions.**
  Specifically: orb-drift animation on the empty state is just "linear infinite
  12s" — not curated. Polish later.
- **Onboarding flow / first-run tour.** App opens straight to the empty-state
  hero with one input. No guided tour. The product is for the owner; he doesn't
  need a tour.
- **Settings panel layout.** Cmd/Ctrl+, opens settings, but the layout (model
  size selector, vocal-isolation default toggle, cache-clear button) is
  unspecified. Defer to v1.1; ship v1 with settings as a plain stack of
  labeled inputs in a `{component.dialog}`.
- **Score history page.** v2 feature. The sparkline `{component.score-card-history-line}`
  is spec'd as v2; v1 ScoreCard is a single attempt only.
- **Drag-to-reorder segments.** Auto-segmented from sentence boundaries; user
  can't manually re-segment. v2 if calibration shows segmentation is bad.
- **Multiple clip thumbnails / video frames.** Sidebar uses initials in a
  surface-strong circle, NOT YouTube video thumbnails. Avoids YouTube branding
  + simpler ingest. v2 if it looks bare in practice.
- **Branded splash screen / app icon.** Owner can drop a placeholder icon now
  and design it later.

### Design decisions deferred (will haunt implementation if left ambiguous)

These are open questions that the implementer will hit during the build. Calling
them out so they don't get answered by accident:

1. **Should the ScoreCard show attempt N of M?** ("Attempt 7 of this segment.")
   Helps user feel progress; risks adding noise to the editorial-instrument-panel
   look. **Default for v1: no, just show the score. Revisit after a week of use.**
2. **Should auto-play of the reference happen on every record click?** (vs
   "user must press play first.") Auto-play feels more shadowing-flow-native
   but can surprise users in a quiet office. **Default for v1: yes, auto-play.
   Add settings toggle in v1.1.**
3. **What is the trim widget's interaction shape exactly?** UI_DESIGN.md
   `{component.dialog-trim}` describes the look but the dual-handle range
   slider needs a behavior spec (does releasing the handle preview a 1s clip?
   does the waveform scrub when handle moves?). **Default for v1: handle
   release shows the trim region duration; no scrubbing preview. v1.1 polish.**
4. **Empty state copy.** I used "Sound like the people you listen to." as a
   placeholder headline. The owner has taste and a YouTube voice — he should
   write the actual hero copy. Not a pre-implementation blocker.

## The Assignment

Before you write a single line of code, do this concrete thing this week:

Pick a 60-second clip from a YouTuber whose voice you want to imitate (Fireship,
Lex, ThePrimeagen — whoever). Type out the transcript by hand. Shadow the clip
ten times into your phone's voice memo, sentence by sentence, slow enough to
match timing. Listen back to attempts 1, 5, and 10.

Then answer three questions in writing:
1. Which words could you not quite catch even after ten reps?
2. Where did your timing drift off the original?
3. Was attempt 10 noticeably better than attempt 1, and how do you know?

Save the recordings. They become your acceptance test for v1. When the app
exists, it has to make this exact ritual easier and more measurable. If after
ten reps you find the practice dull or pointless, the wedge is wrong and we
revisit before any code is written.
